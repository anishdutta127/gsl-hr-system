## Problem Statement

GSL's HR team (Shruti, Riddhi) runs end-to-end hiring on a single shared Excel workbook (`Hiring_Status Q1`). The sheet tracks candidate name, role, source, and a rough pipeline stage in one tab; resumes live as loose PDFs in OneDrive; interview feedback lives in WhatsApp and email; assessments are sent as attachments; there is no shared visibility for HODs (Manali, Shashank, Vishwanath) on their role's pipeline; leadership (Ritu, Ameet, Jesal) have no live dashboard of hiring health; candidates have no self-service. The team is shipping 220+ existing employees on record and 200+ resumes in circulation, growing, with no single system of record and no queryable history.

The system replaces that stack with a Next.js webapp backed by queued GitHub Contents API writes, follows the architecture of `gsl-mou-system` verbatim (same non-negotiables, same CI cadence, same accessibility bar), and is built GSL-first with a clear migration path for a future Mafatlal Group pitch.

## Demand Evidence

- 220+ employee records currently maintained in a single Excel workbook the team edits concurrently.
- 200+ resumes currently maintained as loose OneDrive PDFs with no search, tagging, or deduplication.
- Named requesters: Shruti (HR lead), Riddhi (HR). Anish is the Admin and internal product sponsor. HODs Manali (Academics), Shashank (Ops/STEM), Vishwanath (Premium Sales) confirmed; more TBC. Leadership Ritu, Ameet, Jesal need a dashboard.
- Precedent: gsl-mou-system shipped to a sister team (accounts: Shubhangi, Anita, Pranav) against the same Excel-as-source-of-truth pain. HR team is aware and has asked for a similar tool.
- Parent-company pitch: Arvind Mafatlal Group is a plausible tier-2 buyer once the GSL tenant is proved.

## Status Quo

- Single `Hiring_Status Q1` Excel workbook on OneDrive. All stage transitions are manual edits to a row.
- Resumes, offer letters, assessments delivered via email attachments and WhatsApp.
- Candidate source enum already maintained in Excel: Naukri, Referral, Educohire, Careerchoice, HRTeam, Application, CSS, Other.
- No per-HOD view. No candidate self-service. No alerts or SLAs. No audit trail — changes overwrite in place.
- Previous system of record for employee master is the same workbook; exits are recorded inline.

## Target User & Narrowest Wedge

**Primary user (Week 1 wedge):** Shruti + Riddhi running daily HR ops against the role-level pipeline Kanban. What they need on day one: log in, see every open role with its candidate column stacks, drag a candidate through stages, generate an offer letter. Everything else is week 2+.

**Secondary users (Week 2+):** HOD per-role pipeline view, leadership dashboard, candidate-facing `/careers` + magic-link portal.

## Constraints

- **Hosting:** Vercel Hobby tier. Deploys-per-day quota forces hourly sync cadence and `ignoreCommand` on `^chore\(queue\):`.
- **Stack locked:** Next.js 14.2.x App Router, TypeScript strict, Tailwind v3, Lucide, `docxtemplater` + `pizzip`, JSON data under `src/data/`, writes queued through GitHub Contents API.
- **No in-app AI:** zero API keys, zero billing exposure. Prompt library at `docs/claude-prompts/*.md`; HR uses their own Claude accounts.
- **No file uploads for video:** Drive / OneDrive links only; reviewers click through.
- **Data boundary:** resumes stay on our system (text-searchable); videos are external links; offer letters generated server-side from .docx templates.
- **Domain:** British English, Indian number format (Rs, lakh, crore), never emdash, WCAG 2.1 AA, axe-core in CI with shrinking baseline.
- **Single-tenant clean, not multi-tenant.** (See Premise P7.)

## Premises

Baseline premises taken from the brief, plus three challenges surfaced in this session and resolved below.

**Agreed as-stated:**

1. Fork-in-spirit of gsl-mou-system. Same Next.js 14 / TS / Tailwind stack, same queued-write architecture, same non-negotiables (outputFileTracingIncludes under experimental, ignoreCommand on ^chore(queue): subject-line only, hourly sync + xlsx mtime guard, queue entry shape, per-entity auditLog[]).
2. Per-user staff auth: bcrypt hashes, JWT httpOnly cookies, 7-day expiry, refreshed on activity. Roles: Admin, HR, HOD, Leadership.
3. Video = Drive / OneDrive links. URL validator accepts `drive.google.com`, `docs.google.com`, `1drv.ms`, `onedrive.live.com`, `sharepoint.com`.
4. Zero in-app AI. Copy-paste prompt library at `docs/claude-prompts/*.md`.
5. British English, Indian context, never emdash, WCAG 2.1 AA with axe-core shrinking baseline.
6. Phase 1 excludes: payroll, attendance, leave, appraisals, job-board posting automation, in-app AI, mobile app.

**Challenged and resolved:**

7. **P7 — Multi-tenancy: DEFER.** Single-tenant, clean namespace. All data under `gsl-` prefix. Company name, logo, GSTIN, registered address in `config/company.json`. Hardcoded strings routed through that config from day 1. No `tenantId` columns, no row-level isolation tests, no tenant-scoped magic links. Rationale (user's words): *"Building for a pitch that hasn't happened is the exact trap that kills internal projects."* If Mafatlal materialises, migration is a known 1-2 week effort (add tenantId, backfill gsl, scope queries) — pay that tax when real.

8. **P8 — Timeline: scope commitment, not calendar.** Phase 1 is the scope in the order listed with honest weekly ship-narrow slices. Week 1 ships live to HR: auth + role master + pipeline Kanban (+ offer letter generator as week-1 stretch). HR gets working software in week 2 even if weeks 3-4 scope slips. External commitment: 4-6 weeks end-to-end, usable from week 2. No fixed "done by" date given to HR. Slippage surfaces as "we don't have the assessment engine yet" not "nothing works yet."

9. **P9 — Candidate auth: magic link + session cookie.** First visit: candidate receives signed HMAC magic link (single-use, 15-minute expiry) → server validates and exchanges for httpOnly SameSite=Strict session cookie scoped to that candidate's record, 30-day expiry, rolling refresh on activity. Return visits: cookie active = enter portal. Cookie expired = "check your email for a fresh link" page issues a new magic link. Same `GSL_SNAPSHOT_SIGNING_KEY` HMAC signs both magic links and session cookies.

**Locked in this session:**

10. **Pipeline order: role-configurable.** Role schema gets `pipelineStages: Stage[]` listing interview rounds in order. Default: `[HOD, HR]`. Per-role override allowed. Engine iterates `role.pipelineStages` instead of a global hardcoded enum. Terminal states (Rejected, OnHold, NotInterested, Withdrawn, Offered, OfferAccepted, DocsCollected, Joined) stay global. Future-proofs for Final Round, CEO Round, Technical Panel.

## Approaches Considered

### Approach A: Clone-and-adapt MOU, vertical slices
- **Summary:** Copy MOU's repo layout and library verbatim (`pendingUpdates.ts`, `githubQueue.ts`, queue/audit-log pattern, template registry, sync workflow). Replace MOU entities (MOU, School, PI, Payment) with HR entities (Role, Candidate, Pipeline, Assessment, VideoSubmission, Interview, Offer, Onboarding, Employee, Exit, User). Deliver in vertical slices: W1 auth + role + pipeline Kanban + offer letter live to HR; W2 candidate repo + intake + dashboard + prompt library; W3 `/careers` + portal + assessment + video link; W4 interviews + approvals + onboarding + exit + polish.
- **Effort:** L (4-6 honest weeks, not marketing weeks)
- **Risk:** Low. Every pattern has shipped to production in MOU.
- **Pros:** Fastest to first value. Minimises novel architecture. HR gets W1 slice live in their hands early, which surfaces real usage signal before we build the rest.
- **Cons:** Some MOU patterns (single-user basic auth) must be replaced rather than reused, so there's a non-trivial auth rewrite under the "clone" framing. Also inherits MOU's current quirks (CRLF line endings on Windows, stale golden fixtures in tests).
- **Reuses:** `pendingUpdates.ts`, `githubQueue.ts` (queue writer), `templates.ts` (docxtemplater registry), `next.config.mjs` shape, `vercel.json` ignoreCommand, `.github/workflows/sync-and-deploy.yml`, tokens.css palette, layout primitives.

### Approach B: Library-first extraction
- **Summary:** Before writing HR features, extract MOU's queue writer + audit log + template registry into a shared internal package (`@gsl/core-writes`, `@gsl/templates`). Both MOU and HR depend on it. Future projects (Mafatlal tenant, any new internal tool) inherit the lib.
- **Effort:** XL. Library extraction touches both repos; MOU becomes a migration target; tests must cover both consumers.
- **Risk:** Medium-High. Library abstraction before two real consumers is premature; the right abstraction only becomes visible with HR in place.
- **Pros:** Correct in the long run if we build N ≥ 3 internal tools.
- **Cons:** Delays HR value. Introduces a cross-repo coupling MOU does not need today. Classic premature-abstraction pitfall. Per the user's stated principle: *"Building for a pitch that hasn't happened is the exact trap that kills internal projects."*
- **Reuses:** The MOU code becomes the library.

### Approach C: Thin MVP — intake + pipeline only, defer the rest
- **Summary:** Ship just the candidate repository + pipeline Kanban + offer letter. No assessments, no `/careers`, no candidate portal, no onboarding, no exit. Declare Phase 1 done at the end of week 2. Phase 2 picks up the rest.
- **Effort:** M (2-3 weeks)
- **Risk:** Low.
- **Pros:** Fastest path to a minimal working system.
- **Cons:** Leaves HR still doing half their job in Excel (assessments, candidate communication, offer approval workflow). The "HR still has to maintain two systems" problem undermines adoption — the exact failure mode the office-hours questioning warns against. Also defers candidate-facing surfaces indefinitely, which was the pitch-story angle.
- **Reuses:** Same as Approach A, minus the W3-W4 slices.

## Recommended Approach

**Approach A: Clone-and-adapt MOU, delivered in vertical slices.**

Three reasons.

First, it matches the user's P8 resolution exactly: scope commitment, not calendar commitment, ship-narrow weekly slices, live to HR from week 2. The slicing is the project management mechanic; the architecture choice is clone-and-adapt.

Second, library extraction (Approach B) is the right idea at the wrong time. MOU is one consumer, HR will be two. The correct abstraction needs at least two working consumers before it can be extracted without bending the library to fit the first consumer's quirks. We can revisit extraction when we stand up the Mafatlal tenant (which would make it three) — that's when the tax of not having a library starts to show up in real maintenance drag.

Third, Approach C's scope cut kills the pitch story. `/careers` + candidate portal + assessment + video are the features that distinguish this from "a shared spreadsheet with buttons." If we ship only the internal surfaces, the Mafatlal conversation (when it happens) has nothing to show.

Architecture stays strictly single-tenant per P7. `config/company.json` holds the company identity bundle (name, logo path, GSTIN, registered address, PAN, CIN, signatory name, signatory title, signatory email) and every hardcoded-looking string in templates + UI reads from it. The file is committed (not queued — it's configuration, not transactional data).

## Open Questions

Items that need a decision before or during /plan-eng-review, not blocking this design.

- **Candidate email delivery.** Magic links require reliable transactional email. Phase 1 options: (a) use an existing MAF Technologies SMTP (ops-friction, credential rotation), (b) Resend free tier (100 emails/day, plenty for Phase 1), (c) manual — Anish copies the link from the queued-updates log and forwards to candidate (works for pilot, fails at volume). Default recommendation: Resend with the free tier, review volume after week 4.
- **Assessment engine depth.** Is Phase 1's assessment engine (a) a simple timed MCQ runner, (b) a link-out to whatever existing tool HR uses today, (c) a file-upload-and-manual-grade flow? Shruti's current assessments (Marketing, Instructional Designer, Sr Academics, SME) are .docx files — option (c) is the honest starting point.
- **HOD email addresses vs MAF Technologies SSO.** Are HODs logging in with personal emails + passwords we issue, or do we wire up Microsoft 365 SSO? Phase 1 default: password auth; SSO is a Phase 2 spike.
- **Data sync: Excel or direct entry?** MOU has a canonical Excel source; HR does not yet. Option (a) keep `Hiring_Status Q1` as the source of truth and sync it into JSON (MOU pattern); option (b) cut the Excel dependency at day 1 and enter everything directly into the webapp; option (c) one-time import + direct entry from that point. Default recommendation: (c). Excel loses value once the Kanban exists; forcing both is the two-systems-of-record trap.
- **Candidate source enum additions.** `Hiring_Status Q1` lists Naukri, Referral, Educohire, Careerchoice, HRTeam, Application, CSS, Other. If the team adds LinkedIn Recruiter or Instahyre in future, is that a code change or a data change? Default: data (sources live in `src/data/_enums.json`, editable via the queue like any other entity).

## Success Criteria

## PARKED FOR NEXT SESSION — Premise P14: Self-Maintainability (surfaced 2026-04-23 end-of-session)

**Status: UNDECIDED. Surface this at the start of the next session before any other work.**

Anish surfaced a new architectural requirement late in the 2026-04-23 session: HR should be able to upload files, update content, and maintain the system without developer intervention. Specifically:

- Upload new `.docx` templates (offer letter, appointment letter, relieving letter, experience letter, assessment docx) via admin UI, **versioned** (history preserved), **immediately active** (no redeploy required).
- Edit `config/company.json` (logo, GSTIN, signatory details, registered address, PAN, CIN) through UI, not code commit.
- Edit enum-like reference data (source values, pipeline stage labels, rubric criterion names) through UI.
- Edit email copy, candidate portal "next steps" copy, prompt library entries through UI.
- Add new role types with their own `pipelineStages` + `rubric` + assessment attachment through UI.

This is a **scope expansion** relative to everything committed today. Every committed doc assumes code-committed templates and config. Admin UI is not in any accepted cherry-pick (CP1-CP9). The Engineering plan assumes `config/company.json` is a developer-committed file. The Design review Pass 1 assumed `docs/claude-prompts/*.md` markdown is the prompt library.

Three paths to decide first thing in the next session. **Do not decide now; decide with fresh eyes after Shruti shadow, since her workflow observation may sharpen what "self-maintainable" actually means in practice.**

1. **Fold into Phase 1 and slip timeline.** Scope expands from 4-6 weeks honest to 6-9 weeks honest. HR gets a system they maintain from day 1.
2. **Phase 1 ships code-committed assets. Admin UI as Phase 1.5.** HR uses the system in its current form for ~4 weeks. Admin UI drops in as a focused 2-3 week follow-up, informed by what HR actually tried to change during those 4 weeks.
3. **Both as Phase 1 with a tighter cut elsewhere.** Keep the 4-6 week target. Cut something already accepted (candidate cathedral? leadership dashboard? rubric structure?) to make room. Harder tradeoff because accepted cherry-picks were already the value drivers.

### Architectural shape (either way)

When this decision lands, the following spike into the eng-review plan:
- Template storage moves from `public/hr-templates/*.docx` (committed) to a queue-managed directory with per-version metadata (`{id, filename, uploadedBy, uploadedAt, activeAt, replaces}`). `outputFileTracingIncludes` still covers the path.
- `config/company.json` becomes `src/data/_company.json` (queue-written) + a schema validator run at every write.
- Enum editing adds `src/data/_enums.json` (already planned as data-editable for source enum additions) — extended to cover pipeline stage labels, rubric criteria, email subject templates.
- Prompt library moves from `docs/claude-prompts/*.md` to `src/data/prompts.json` (queue-written) + the CP3 in-app drawer renders from it directly.
- Admin-only routes gated behind `requireAdmin` middleware (already spec'd in eng review).
- File upload for .docx templates — new validator + queue write path + storage location. Max size constraint (8MB for .docx vs 5MB candidate resume). MIME-sniff at server.

### Information Architecture

**Home (post-login):** needs-attention feed first. Primary view = every candidate awaiting this user's action across all their roles, grouped by action type (review, score, schedule, generate offer). Secondary = open-roles summary. Tertiary = global search. ⚠️ HR-workflow-dependent, re-check with Shruti shadow notes.

**Role Kanban (`/roles/[id]`):** role selector at top, stage columns per `role.pipelineStages`, horizontal scroll. Card density = medium: name + source badge + days-in-stage indicator (~72px card height, 6-8 visible per column without scroll at laptop height). Click → bottom sheet on mobile (per `bottom-sheet-for-expand`), inline drawer on desktop. Drag between columns transitions stage.

**Candidate detail (`/candidates/[id]`):** identity block + actions top, timeline middle, per-application sections (nested interviews/assessments/videos/offer/onboarding) below. Desktop sidebar jump-to list; mobile bottom sheet on action tap.

**HOD rubric interview form:** candidate identity mini-card top; role rubric rendered as labeled scored inputs (scale driven by `role.rubric[].scale`); per-criterion short notes; live aggregate score at bottom (weighted average); overall notes textarea (16px minimum, per `ios-textarea-zoom-16px`); recommend proceed/hold/reject radio.

**Offer drafting (`/offers/[id]`):** desktop split view, form 40% left + preview 60% right, live re-render on every edit. Mobile stacked with "see preview" expandable. Approve + generate disabled until all required placeholders filled; tooltip lists missing fields.

**Prompt drawer (CP3):** sidebar "Prompts" entry invokes right-rail drawer (40% width desktop, full-screen modal mobile). Contents: search, category chips, scrollable prompt list. Selected prompt shows title + use-case + copy button + schema preview + example outputs + favourite. Paste-back validator is a separate tab within the same drawer.

**Global dashboard (`/dashboard`) — Phase 1 basic version:** needs-attention feed (shared component with Home), KPI row (open roles, open offers, in-flight candidates, joined this month), role-by-role count aside. Leadership read-only mode = same surface, no action buttons. CP6 expansion triggers at 30-day leadership-usage signal.

## Candidate-facing Surfaces Design Decisions (from /plan-design-review Pass 2, 2026-04-23)

Pass 2 of the design review. Calibrates against DESIGN.md (landed earlier in this session). Text-based review chosen over mockup generation — the user's stance (saved as cross-session memory) is that plan-stage AI mockups add noise once DESIGN.md exists and /frontend-design produces real UI at implementation time.

### Information Architecture (per candidate surface)

**`/careers` public listing:** brand + tagline + **filter chips (team / location / role-type)** + scrollable role list. No marketing hero, no 3-column feature grid, no "why GSL" section above the fold. About-GSL block at page bottom as prose.

**`/careers/[roleId]` role detail:** role title + one-sentence "what you'll do" + Apply CTA (sticky bottom on mobile) + full role detail (what-you'll-do, responsibilities, must-haves, nice-to-haves, salary range if disclosed, location, role-type) + application form (name/email/phone/resume/cover note) + team info + "what happens next" timeline.

**`/portal/welcome` (post-magic-link CP1):** welcome card single-focus. Fraunces greeting + current-stage plain-English summary + recruiter contact card + primary CTA for next action. Nothing else on screen.

**`/portal/me` (returning view):** vertical-timeline progress-viz primary; next-action card secondary; application details + recruiter contact tertiary.

**`/portal/assessment/[id]`:** full-screen takeover. Timer top-anchored (JetBrains Mono), one question at a time (18 px body), stacked answer input (48 px touch targets), sticky "Save and exit" + "Next" bottom. No nav chrome.

**`/portal/video/[id]`:** instructions + URL input with supported-hosts hint + submit.

**`/portal/withdraw/[applicationId]` (CP8):** single-focus confirm. Question + optional reason dropdown + freeform notes + confirm (danger colour) / cancel.

**`/portal/request-new-link`:** single-focus status. Resend-countdown + rate-limited resend button.

### Interaction State Coverage (candidate-side)

All five states (loading / empty / error / success / partial) specified per surface in Pass 2 table. Key copy commitments:

- `/careers` empty: *"Check back soon."* Phase 1; waitlist-subscribe is Phase 2.
- `/careers/[role]` form network error: *"We couldn't reach our server. Your details are saved — try again in a moment."*
- `/portal/welcome` invalid link: redirect to *"This link isn't recognised"* page with *"Request a new link →"* CTA.
- `/portal/assessment` network drop: *"Saved locally. Reconnecting…"* with silent queue flush on reconnect.
- `/portal/video` URL rejection: *"Only Drive, OneDrive, SharePoint links accepted."*
- `/portal/withdraw` success: *"Your application has been withdrawn. Thanks for letting us know."*
- Rejection UX: portal shows *"Application ended"* plainly. No generic canned reason. No corporate softening. Sets the stage for CP9 upgrade when HR actually writes feedback.
